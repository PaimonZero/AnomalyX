## 2. Technical Implementation Details

### Component 1: Redis Rolling Aggregates
- **State Store:** Uses Redis Sorted Sets (`anomalyx:agg:{sender_id}:sent` and `anomalyx:agg:{receiver_id}:received`) where members are JSON-serialized transaction records and scores are unix timestamps.
- **Windowing:** Transactions are dynamically pruned beyond 24 hours (`ZREMRANGEBYSCORE`). All rolling metrics are calculated relative to the incoming transaction's timestamp, supporting historical replay in tests.
- **In-Memory Fallback:** Built an automatic local dictionary-based sliding window fallback when Redis is offline or testing in quick-mode.
- **Rule Engine & ML Alignment:** `configs/rules.yaml` rules have been migrated to the new real feature names (e.g. `count_just_below_threshold_24h`, `sum_amount_1h`, etc.) and whitelisted in `ALLOWED_CONTEXT_NAMES`.

### Component 2: Explanation Cache
- **Fingerprinting:** Cache keys are generated by hashing the sorted triggered rule IDs and bucketed top SHAP features (rounded to 1 decimal place to group similar patterns):
  ```python
  fingerprint = f"rules:{','.join(rule_ids)}|features:{','.join(bucketed_features)}"
  cache_key = f"anomalyx:exp_cache:{md5(fingerprint)}"
  ```
- **Operational Integration:** Background tasks check the cache first. If hit, the explanation is retrieved from Redis/local cache, tagged `source="cache"`, and logged to Prometheus.
- **DB Safety:** Complies with the database check constraints (persists `explanation_source` only as `llm` or `template`), while recording the true `"cache"` source to Prometheus metrics.

### Component 3: Geo/Device Anomaly (Full Profile)
- **Profile Collection:** Tracks all device IDs and countries/regions used by each sender in the last 24 hours.
- **Anomaly Logic:**
  - `new_device`: True if the current device has not been seen in the sender's history.
  - `geo_anomaly`: True if the current country/region differs from the most frequent (mode) historical location.
  - `impossible_travel`: True if the sender transacted from a different country in the last 1 hour.
- Triggering: Anomaly flags feed directly into the whitelisted rule engine features, causing rule `R-GEO-01` to trigger on SG SG/VN-style impossible transitions.

### Component 4: Score Drift Metrics (PSI)
- **Mathematical Formula:** Computes PSI over a rolling predictions deque (size 1000) against the baseline distribution using 10 equal-width bins in $[0, 1]$:
  $$PSI = \sum (Actual\% - Expected\%) \times \ln(Actual\% / Expected\%)$$
- **observability & Metrics:**
  - Exposes `anomalyx_model_drift_psi` and `anomalyx_feature_drift_psi` gauges.
  - Syncs the real PSI value with the legacy `anomalyx_model_drift_placeholder` so that the React monitoring screen gets real drift data out-of-the-box.
- **REST Endpoints:**
  - `GET /api/v1/drift/status`: Returns current PSI, window counts, and classification (`NO_DRIFT`, `WARNING`, `DRIFT`).
  - `POST /api/v1/drift/baseline`: Allows ML engineers to hot-swap baseline distribution arrays.

## 4. Manual Verification Steps

1. **Local verification:** Ensure the docker services postgres and redis are active.
2. **Submit Predictions:** Submit predictions for a sender. Verify that the rolling counters increase (first txn features show 1 count, subsequent txns accumulate).
3. **Trigger Alert & Explanation:** Trigger an alert. The first explanation logs a cache miss, while the second prediction of an identical pattern logs a cache hit.
4. **Inspect Metrics:** Query `GET /api/v1/metrics`. Confirm that `anomalyx_model_drift_psi`, `anomalyx_feature_drift_psi`, and `anomalyx_explanation_cache_hits_total` are populated and present.
